## Fair baseline and discriminating probes

The ordinary arm should use the normal saved brief, manifest, candidate hash, factual acceptance checks and bounded feedback described in the proposal. Allow it to consult its saved records after a fresh coordinator process starts. Removing these ordinary practices would manufacture a weak baseline. Tests, explicit identifiers, files, SQLite and content hashes are not unique advantages of Genie.

Use matched, controller-generated metadata substitutions: wrong arm/task, input hash, attempt and stale candidate hash. Both arms must reject through their specified ordinary checks or runner callback binding. Score whether an incorrect result was accepted and whether a valid result was unnecessarily held. The runner's additional slot/call token is a mechanism-specific check, not evidence that the baseline failed an identical token contract it was never given. Preserve each probe's intended substitution and observed response.

A fresh coordinator subprocess can inspect persisted state in both arms while the Work host remains alive. State exactly what was read: saved candidate/manifest/check record for ordinary work; queue, journal, workflow and fresh destination evidence for Genie. This probes local continuity and recovery bookkeeping. It does not test host death, remote callback authenticity, whole-store rollback resistance, power-loss durability or unattended model dispatch. Do not introduce another worker call merely to manufacture a restart.

Genie's inbox application/fresh readback should be scored as its configured completion behavior. Use an ordinary owned output file plus fresh candidate-hash readback for the baseline's delivery equivalent. A missing baseline sink receipt is not a functional failure when its delivery contract is a file. Conversely, neither historical completion nor a top-level diagnostic PASS substitutes for current exact-output readback.
