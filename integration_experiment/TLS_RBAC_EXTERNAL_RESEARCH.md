# Current primary-source research: etcd 3.6 TLS + RBAC

Retrieved 2026-10-04 UTC. Scope is the exact proposed etcd 3.6.5 fixture, not production security guidance.

1. **TLS endpoint behavior:** [etcd v3.6 transport security](https://etcd.io/docs/v3.6/op-guide/security/) documents server TLS and optional client-certificate checks. [Configuration](https://etcd.io/docs/v3.6/op-guide/configuration/) says `--trusted-ca-file` also enables client-certificate auth, so it must not be set when this fixture intends server-auth TLS plus username/password RBAC without requiring client certificates. Server cert/key enable HTTPS; generated CA is supplied by the Python client's trust store.
2. **HTTP/gRPC listeners:** [v3.6 configuration](https://etcd.io/docs/v3.6/op-guide/configuration/) states `--listen-client-urls` serves gRPC and HTTP unless `--listen-client-http-urls` is set; the latter is HTTP-only. Keep one HTTPS listener serving the gateway for this bounded test and record the exact flags.
3. **Gateway authentication:** [v3.6 gRPC gateway](https://etcd.io/docs/v3.6/dev-guide/api_grpc_gateway/) documents `/v3/auth/authenticate`, use of the returned token in the HTTP `Authorization` header, and gateway HTTP error mapping. It also states gateway authentication by TLS Common Name is unsupported. Therefore the harness must use the bearer token for the fixture user and must not infer a user principal from TLS CN.
4. **RBAC boundaries:** [v3.6 RBAC](https://etcd.io/docs/v3.6/op-guide/authentication/rbac/) documents user/role setup, prefix range grants, and notes `/health` and `/metrics` are not V3 RBAC protected. Tests must exercise protected KV operations and must not treat those endpoints as proof of authorization or current authority.
5. **Token type limitation:** [v3.6 authentication design](https://etcd.io/docs/v3.6/learning/design-auth-v3/) says the default simple token is for development testing, not production; it also documents a stateful-token race that may yield `invalid auth token` under latency. This harness may use the pinned fixture's simple token only as a disposable test credential. Any such intermittent auth response stays a failure/indeterminate; no retry may be used to turn a failed protected operation into an authority success. No production token-mode claim follows.
6. **Gateway errors:** v3.6 gateway documentation says HTTP status is the primary success/failure signal and describes v3.6's `google.rpc.Status` error body. The harness records HTTP status for denied calls and does not persist error bodies; an HTTP success alone is not sufficient for the application's transaction result.
7. **Exact RBAC wire schema:** the pinned [etcd v3.6.5 `rpc.proto`](https://github.com/etcd-io/etcd/blob/v3.6.5/api/etcdserverpb/rpc.proto) defines `AuthRoleGrantPermissionRequest` as a role `name` plus nested `authpb.Permission perm`; the pinned [`auth.proto`](https://github.com/etcd-io/etcd/blob/v3.6.5/api/authpb/auth.proto) places `permType`, `key`, and `range_end` inside `Permission`. The first run's etcd log showed the top-level fields were ignored, leaving no permission. The exact nested JSON candidate is `{"name": role, "perm": {"permType": "READWRITE", "key": base64(prefix), "range_end": base64(prefixEnd)}}`. Verify it against the pinned server using `AuthRoleGet` readback before enabling auth.

These primary docs are current as retrieved, but exact behavior remains to be tested against the pinned v3.6.5 binary. Documentation supports a test fixture, not independently administered PKI, credential custody, lifecycle-bound provider identity, or production deployment conformance.
